# node-radar 流程审计（2026-11-06）

## 当前真实链路

- `discover.yml` 每周搜索公开仓库，验证候选订阅文件后更新 `sources.auto.json`。
- `aggregate.yml` 每 6 小时合并人工源与自动源，解析/去重并生成 Clash 订阅，使用 Mihomo 校验后提交 `dist/` 和源健康状态。
- `speedtest.yml` 每 6 小时从聚合结果抽样，在 GitHub Actions（美国出口）经 Mihomo 实测吞吐，生成速度报告和极速订阅。
- 本项目只聚合公开节点，不代表自建隧道，也不等于用户本地网络质量测试。

## 已执行

- 三个会写仓库的工作流统一使用 `node-radar-publish` 并发组，避免 discover、aggregate、speedtest 的提交互相踩踏。
- 聚合发布前要求主订阅和 summary 文件存在且非空；不再因输出文件缺失而跳过内核验证后继续提交。
- 测速输入缺失、节点为空或 Mihomo 控制器无法启动时返回失败，不再以 exit code 0 伪装成功。
- 当有效测速节点不足以生成极速订阅时，删除旧的 `speed-top.yaml`，避免旧结果继续被误认为当前结果。
- 测速工作流同步处理极速订阅删除，确保线上文件与本轮结果一致。

## 仍需处理

1. 自动发现的源直接进入聚合生产链。建议增加隔离阶段：新源先进入候选清单，连续多轮通过内容解析、Mihomo 校验和异常字段检查后再提升；人工源保持最高优先级。
2. 当前聚合器的探测语义是“源能抓取且可解析”，不是“节点在用户所在地可用”。README 已说明不做存活探测；不要把 GitHub runner 的可达性包装成用户侧健康结论。
3. 测速仅代表 GitHub Actions 美国出口。应在报告和订阅元数据中持续保留 vantage、测试目标、负载大小、测试时间；不要用它覆盖本机到 CF 的优选结果。
4. `speedtest.mjs` 用节点名称回映测速结果；同名节点可能导致极速订阅多选或误选。后续应使用稳定的节点指纹（协议/服务器/端口/传输参数摘要）或本轮唯一索引。
5. Mihomo 使用 latest release，构建不完全可复现。建议固定经过验证的版本，并由 Dependabot/定时任务单独提升级别。
6. 三个 workflow 已串行，但 GitHub concurrency 只保留一个待执行项；频繁手动触发可能合并/替换等待中的任务。长期应改为单一 dispatcher + 显式队列，或把发现、聚合、测速拆成独立产物阶段，最后由唯一发布者提交。

## 建议目标结构

`sources-curated.json`（人工可信） + `sources-candidate.json`（自动发现隔离） → 解析/格式门禁 → 聚合产物 → Mihomo 固定版本验证 → 独立测速产物 → 单一发布工作流原子更新 `dist/` 和健康状态。
